# HackCore — project structure and how to use it

This is the map of the template. How to install and run it is in [SETUP.md](SETUP.md). Design colors are in [apps/frontend/DESIGN.md](../apps/frontend/DESIGN.md). Mock endpoint status is in [MOCK_INVENTORY.md](MOCK_INVENTORY.md).

---

## What this project is

HackCore is a starter for a 24-hour hackathon. It already has:

- a React website (`apps/frontend`)
- a Fastify API (`apps/backend`)
- Postgres in Docker
- login with roles (`admin`, `manager`, `member`)
- one sample feature called **Records** (list, create, edit)

When the problem statement arrives (inventory, quotations, clubs, payroll), you build on top of this. You do not rebuild login, database wiring, or the folder pattern.

```text
TemplateRepo/
├── apps/
│   ├── backend/             Fastify + Postgres (package filter: backend)
│   └── frontend/            React + Vite (package filter: frontend)
├── docs/

│   └── MOCK_INVENTORY.md    which endpoints are real vs mocked
├── docker-compose.yml       starts Postgres
└── package.json             root commands (pnpm dev, db:seed, ...)
```

```text
Browser (React)
    │
    │  always calls /api/... through api-client.ts
    │
    ├─ mock mode ──► MSW handlers pretend to be the server
    │
    └─ real mode ──► Fastify ──► Drizzle ──► Postgres
```

The React pages never know which path was used. That is the point: UI people can work before the backend is finished.

## Backend structure (`apps/backend`)

```text
apps/backend/src/
├── index.ts                 starts the server
├── app.ts                   registers plugins + feature routes
├── plugins/                 shared server tools (NOT product features)
│   ├── auth.ts              JWT verify, requireAuth, requireRole
│   ├── db.ts                attaches Drizzle / Postgres to Fastify
│   └── errors.ts            common error responses
├── features/                one folder per product area
│   ├── auth/
│   │   ├── schema.ts        Zod: what login/signup body must look like
│   │   ├── service.ts       password hash, create user, find user
│   │   └── routes.ts        POST /api/auth/login, signup, me
│   ├── records/
│   │   ├── schema.ts
│   │   ├── service.ts
│   │   └── routes.ts
│   └── health/
│       └── routes.ts
├── db/
│   ├── client.ts            Drizzle client
│   ├── pool.ts              Postgres connection
│   ├── migrate.ts           applies Drizzle migrations
│   ├── schema/              table definitions (users, records, ...)
│   └── seeds/               demo users and starter rows
└── lib/                     tiny helpers (validate, ServiceError)
```

Migrations generated by Drizzle live in `apps/backend/drizzle/`.

### Plugins vs features (important)

| Word | Meaning | Where |
| --- | --- | --- |
| **Feature** | A product area the user cares about | `src/features/auth`, `src/features/records` |
| **Plugin** | Shared machinery every feature uses | `src/plugins/` |

Signup and login are a **feature**.  
Checking the JWT token is a **plugin**, because quotations and inventory will need the same check and must not rewrite it.

Fastify calls shared registered pieces “plugins.” That is why the folder is named that way. Do not put business features inside `plugins/`.

### What each feature file does

For every new backend feature, copy `features/records` and keep these three files:

1. **`schema.ts`** — request shape (Zod). Rejects bad JSON early.
2. **`service.ts`** — business rules + Drizzle queries. No Fastify objects if you can avoid them.
3. **`routes.ts`** — HTTP path, role check, call the service, return JSON.

Tables go in `db/schema/<feature>.ts`, then:

```bash
pnpm db:generate
pnpm db:migrate
```

Register the route in `app.ts`.

### How a real request moves

```text
POST /api/records
  → routes.ts      requireRole("admin","manager") + Zod body check
  → service.ts     createRecord(...)
  → Drizzle        INSERT into records
  → routes.ts      { success: true, data: ... }
```

## Frontend structure (`apps/frontend`)

```text
apps/frontend/src/
├── app/
│   ├── main.tsx               starts React; turns MSW on in mock mode
│   ├── App.tsx                URL routes (/login, /app/records, ...)
│   ├── AuthProvider.tsx       stores the logged-in user + token
│   ├── AppShell.tsx           header and nav
│   └── feature-registry.tsx   list of screens (add one object per feature)
├── features/
│   ├── auth/                  login + signup pages
│   └── records/               list / create / edit example
├── components/ui/             Button, Table, Dialog, Select, ...
├── lib/api-client.ts          every network call goes through here
├── mocks/                     fake API for UI-only work
└── styles/tokens.css          colors from DESIGN.md
```

### Frontend feature folder

Copy `features/records`:

```text
features/quotations/
  types.ts
  quotations.api.ts      thin wrappers around apiClient
  hooks/useQuotations.ts
  pages/QuotationsPage.tsx
  components/...
```

Then add one entry in `feature-registry.tsx` so the nav shows it.

### How authentication works on the website

1. User signs in on `/login`.
2. API returns a JWT token.
3. `AuthProvider` saves the token in `localStorage`.
4. `api-client.ts` adds `Authorization: Bearer <token>` on every request.
5. On refresh, the app calls `/api/auth/me` to restore the user.
6. Nav items can hide screens by role using `roles` in the feature registry.

## How mock handlers work (simple language)

### The idea

Sometimes the frontend person is ready before the backend person.

Instead of waiting, we turn on **mock mode**. The browser still calls `/api/records`, but a library called **MSW** (Mock Service Worker) intercepts that call and answers with fake JSON. The React code does not change.

Think of it like a understudy actor: same lines, same stage, temporary cast.

### Two modes

| Command | Mode | Who answers `/api/...` |
| --- | --- | --- |
| `pnpm dev` / `pnpm dev:real` | real | Fastify + Postgres |
| `pnpm dev:mock` | mock | MSW handlers in the browser |

In production, mock mode is blocked.

### What happens when you open the app in mock mode

1. `main.tsx` sees `VITE_API_MODE=mock`.
2. It starts the MSW worker (`mocks/browser.ts`).
3. The worker registers handlers from `mocks/handlers/`.
4. When React calls `apiClient.get("/records")`, the browser first hits MSW.
5. MSW finds a matching handler and returns the fixture JSON.
6. React renders the table as if the real server had answered.

If no handler matches, MSW lets the request go through (`onUnhandledRequest: "bypass"`).

### Example: listing records

Real code in the page (does not change between modes):

```ts
const response = await apiClient.get("/records");
// response = { success: true, data: [ ...records ] }
```

In **real mode**, that request goes to Fastify → Postgres.

In **mock mode**, this handler answers instead (`mocks/handlers/records.handlers.ts`):

```ts
http.get("/api/records", ({ request }) => {
  if (!userFromRequest(request)) {
    return HttpResponse.json(
      { success: false, message: "Authentication required." },
      { status: 401 }
    );
  }
  return HttpResponse.json({
    success: true,
    data: records   // from fixtures/records.fixture.ts
  });
});
```

So the page still gets `{ success: true, data: [...] }`. It cannot tell that the rows never touched Postgres.

### Example: creating a record as a member

1. Member logs in (mock login handler issues a fake token).
2. Page calls `POST /api/records`.
3. Mock handler checks the user’s role.
4. Role is `member` → returns **403 Forbidden**, same as the real API.
5. The UI can show the “no permission” state without a backend.

That is why mocks mirror roles: UI people can build role screens early.

### Where mock files live

```text
apps/frontend/src/mocks/
├── browser.ts                 starts MSW
├── session-store.ts           fake users + tokens for mock login
├── fixtures/                  sample JSON rows
└── handlers/
    ├── index.ts               registers all handlers
    ├── auth.handlers.ts
    └── records.handlers.ts
```

### Rules (do not break these)

1. Never put fake business data inside pages or components.
2. Never fall back to mock data if the real API fails.
3. Every temporary mock endpoint needs a handler + fixture.
4. Keep [MOCK_INVENTORY.md](MOCK_INVENTORY.md) updated.
5. Always demo the final product with `pnpm dev` (real mode). Judges will refresh the page; data must still be there.

## Day-of hackathon workflow

1. Read the brief. Agree on roles and main screens.
2. One person owns the database tables in `apps/backend/src/db/schema/`.
3. Same person (or another) owns `features/<name>/{schema,service,routes}.ts`.
4. Other teammates each take one frontend feature folder + one registry entry.
5. If UI is ahead, add MSW handlers so screens can keep moving.
6. Wire real API, then switch everyone to `pnpm dev`.
7. Seed realistic demo accounts for the judge walkthrough.

Copy **Records** on both sides. Do not invent a second pattern mid-event.

## Recommendations to win the time (and look strong)

### Must do

1. **Keep the three-file backend feature pattern.** Routes thin, logic in service, Zod in schema.
2. **Demo only on real mode.** Refresh the page live for judges.
3. **Prepare 3 demo logins** that match the brief (for example sales_rep / manager / customer).
4. **One person owns schema conflicts.** Do not have four people editing `db/schema` at once.
5. **Write seed data that tells a story.** Empty tables look unfinished.
6. **Use roles on purpose.** Judges notice “member cannot approve, manager can.”

### Should do if you have time

7. **Add a tiny checklist page** in the README for your team: who owns schema, API, screen A, screen B.
8. **Keep MOCK_INVENTORY.md honest.** It helps when someone asks “is this real yet?”
9. **Stick to DESIGN.md colors.** Off-palette reds/greens look rushed.
10. **Prefer one deep happy path** over five half screens. A complete create → negotiate → approve flow beats four empty list pages.

### Avoid

11. Hardcoding sample employees/quotes inside React components.
12. Putting feature logic into `plugins/`.
13. Rewriting folder structure mid-hackathon.
14. Switching package managers mid-event. Install pnpm once: `npm install -g pnpm`.
15. Building a generic “workflow engine.” A `status` column + `requireRole` is enough for most briefs.

### Small architecture tips that look good to judges

- Name statuses clearly: `draft`, `submitted`, `approved`, `rejected`.
- Put transitions in `service.ts` (`approveQuote`, `rejectQuote`), not in the React page.
- Return the same envelope everywhere: `{ success, data, message? }`.
- Keep API paths boring and REST-like: `/api/quotations`, `/api/quotations/:id/approve`.

## Design tokens (short)

Source of truth: `apps/frontend/DESIGN.md`. Runtime CSS: `apps/frontend/src/styles/tokens.css`.

| Token | Hex | Use |
| --- | --- | --- |
| Ink | `#0f172a` | text, borders, primary buttons |
| Canvas | `#f8fafc` | page background |
| Card | `#ffffff` | surfaces |
| Success | `#10b981` | active / approved |
| Warning | `#f59e0b` | pending / mock banner |
| Danger | `#f43f5e` | errors / rejected |

No gradients. No emoji in the UI. Use Lucide-style icons or Badge text.
